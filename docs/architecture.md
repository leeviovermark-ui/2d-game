# Authority and persistence

## Boundaries

`client/main.gd` composes the Godot presentation. `network.gd` handles WebSocket lifecycle and sends intents. `state.gd` applies server snapshots/deltas and reconciles local movement prediction; `movement.gd` mirrors the authoritative movement model. `landscape.gd` renders visible tiles, players and parallax; `ui.gd` owns the HUD/login and `panels.gd` owns gameplay panels; `admin_panel.gd` provides the administrator interface; `slot.gd` implements drag/drop; `art.gd` and `audio.gd` produce original assets.

`server/main.py` is the bounded network gateway and fixed 60 Hz simulation loop. `game.py` validates gameplay and routes world-scoped events; `physics.py` implements movement, collision clipping, variable jump height, coyote time, and buffered jumps. `trading.py` owns the exchange state machine and `admin.py` owns authorized moderation and grants. `world.py` owns generation, collision, and safe spawn search. `inventory.py` provides copy-based transfers and stack operations. `storage.py` persists accounts, inventories, tile deltas, crops, containers, drops, sessions, replay IDs, administrator roles, moderation, and audit records. `shared/definitions.json` supplies item/recipe/movement definitions to both runtimes.

Normal gameplay intents cannot set positions, create items, choose drop rewards, set inventory, accelerate mining, mature crops, change another owner's permissions, or exchange assets directly. Movement packets contain axis, jump-edge, jump-held, sequence, and movement-epoch information. The server consumes at most one queued input frame per simulation step, ignores stale sequence numbers and packets from an earlier world/connection epoch, bounds the queue, and stops stale input. Client prediction provides immediate feedback while server acknowledgements correct its state. Mining completion uses the server clock, the selected tool, current tile, permission, and reach. Placement removes one item only after bounds, occupancy, support, player overlap, ownership, and quantity checks. Spawns choose the nearest clear, supported position in both axes instead of preferring the highest platform in a column.

## Transactions

WebSocket handlers call synchronous authority operations with no suspension inside a transaction. One process serializes SQLite `BEGIN IMMEDIATE` transactions. Inventory transfers/crafting work on copies; validation failure discards them. Valuable requests have persistent per-account replay IDs. The cache and pending events roll back with a failed request. Drops are consumed once, and chest transfers re-read the current container instead of trusting a client's stale slots.

A trade freezes inventory mutation and pickup, then requires two locks and two confirmations on the current offer revision. Every offer, lock, confirmation, and active cancellation names its unique trade ID, so delayed packets cannot act on a replacement trade. Any offer change resets all acknowledgements. The server rechecks item quantities, range, both players and capacity before writing both inventories and an audit record in the same transaction. Final validation failure rolls back the economy and closes the trade for both players; no items are exchanged and inventory controls are released. No assets are removed just to form an offer. Disconnect, world travel, closing the panel, account takeover, and leaving range also cancel safely.

Mining completion and pickup write their tile/drop/inventory changes before publishing cache changes and events. A database failure therefore leaves the collectible or tile available for a later retry rather than producing a ghost item. Mining an empty chest also removes its obsolete container row.

## Administrator access

Typing `/addomen` requests the administrator panel; it does not grant a role. The server checks the persisted role on every action. Administrators can grant catalog items, kick, ban/unban, mute/unmute, and move an explorer to a world's validated spawn. Grants use full-capacity validation and reject active trades. Moderation and grants are audited; bans invalidate sessions and prevent sign-in/resume. Kicking or banning an online explorer cancels their trade and saves their inventory before disconnecting them. Administrators cannot kick, ban, or mute themselves or another administrator through this menu.

For the default loopback listener, the oldest existing account becomes the local owner when no administrator has been configured; for a new save, the first account becomes that owner. A public listener requires explicit `--admin NAME` configuration and never makes the first visitor an administrator. Named roles persist across restarts. Create and secure the intended account locally before exposing a named administrator on a public listener.

## Persistence and performance

Schema 2 uses SQLite WAL and foreign keys. Its migration from schema 1 adds administrator and moderation tables while preserving existing saves. Initial terrain is reconstructed from a saved generation seed/biome; generation remains unchanged so existing worlds retain their terrain. Only changed tile rows are written. Crops store planted timestamps and need no unloaded-world tick. Drops and chest contents persist. Changed inventories commit immediately; movement checkpoints occur every two seconds and on a clean disconnect/shutdown. An abrupt crash can roll position back by up to two seconds; committed items and tile changes survive. The schema version is checked rather than silently rewriting an incompatible database.

Active worlds alone live in the authority cache. Clients receive an initial bounded-world snapshot on entry, world-scoped entity snapshots at 20 Hz, and tile/drop/storage/metadata deltas after mutations. Rendering visits only the viewport's visible tile region. Requests retain rollback copies of player/trade state and only the world they can mutate; selections and trade actions no longer copy every cached terrain map. Per-connection bounded writers keep a slow socket from blocking the simulation. Password scrypt hashing runs outside the event loop, with at most four concurrent gateway authentication operations; SQLite finalization stays on the authority thread and rechecks account state after hashing. A mutation journal and chunked interest regions remain extension paths before increasing world/player limits. The 100-world creation cap is an explicit development limit.

## Extension paths

Stable item IDs, central recipes, and item categories can add new blocks and stations without duplicating registries. Timestamped crops illustrate the offline-processing model for future machines. Delta tables and world routing can evolve toward chunk snapshots/interest regions. Economic audit and atomic inventory operations can support shops and market transactions, but neither system exists yet. Logic objects and combat should be separate authoritative components, never client-awarded effects.

Tests may construct authority state directly inside an isolated database; those helpers are not exposed to players. Remote deployment still needs TLS termination, backups, account recovery, operational metrics, and load testing beyond this local development slice.
